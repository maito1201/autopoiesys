# 判定者が「疑う所」と「信用してよい所」を機械が切り分ける

## 受け入れ条件（実装の結果を見る前に固定する）

1. briefingの検証実績の各行に**鮮度**が機械で付く: その記録より後に成果物が変わっていれば
   「この記録は古い状態への検査（再実行が要る）」、変わっていなければ「現在の状態への検査」
2. briefingが信用の境界を明示する。信用してよいのは決定的記録の**事実**（いつ・どのコマンドが・
   どの終了コードと出力を返したか）だけで、(a) 記録はその時刻の状態しか語らない
   (b) 実行された検査の範囲しか語らない (c)「だから要件を満たす」は記録に含まれない、を明記する。
   実行者の散文は証拠にならないという既存の規律は変えない
3. `codemap` コマンドが、リポジトリの目次（コアのモジュール・検出器・evaluator・golden・
   テスト件数）を**決定的に**生成する。判定者の散文・申告は一切含まない
4. briefingに目次が入り、「これは目次であって証拠ではない。根拠にするなら実物を開け」と明記される
5. `node --test` 全件・`regression` 全件・docs-drift・skill-commands が通る
6. 実測: briefingのトークン増加分と、次の判定サブエージェントの消費を記録する
   （増えたら失敗と書く。n=1では証明にならないことも書く）

## 前提の棚卸し

| 前提 | 出所 | 対処 |
|---|---|---|
| 疑う所と信用する所を切り分けて改善を試みる | ユーザー指定 | 固定制約 |
| 決定的記録の再実行から生まれた指摘は0件（T017・T019・T020の判定3本とも一致） | 測定 | n=3。だから再実行を禁止せず、鮮度と範囲で条件づける |
| 判定者の消費の相当部分は方向づけ（地図の作り直し） | **未測定の推定** | 目次で減るかを受け入れ条件6で測る。減らなければそう書く |
| 記録装置そのものの正しさは golden と検出力テストが保証している | 設計（F008の是正） | この前提が崩れたら信用の境界も崩れる。地図に golden 件数を出して見えるようにする |
