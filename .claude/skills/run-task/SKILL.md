# run-task

このループの制度は4つの事実でできている。守らせるのは説教ではなくコードパスである:

1. **納品と検収は分離されている。** 全評価PASSは「納品してよい」（DELIVER）であって完了ではない。
   納品物は「宣言 + 反証手続き」の形でしか受理されず、検収は現実（コマンド・時間・ユーザー）が行う。
   剥がれた宣言（broke）はタスクをopenへ戻し、較正台帳に恒久に残る。
2. **あなたは持続する自己を持つ。** 宣言が実行を生き延びた記録（較正）はタスク類型ごとに蓄積され、
   task new のたびに文脈へ返ってくる。較正が良い類型はllm_judgeが抜き取り検査になり（監査率が下がり）、
   宣言が剥がれれば全数監査に戻る。**裁量は実績が買う。**
3. **元帳は現実だけから書かれる。** deterministicの検収・verdictはCoreがコマンドを実行して書いた行であり、
   自己申告では書けない。監査の抽選も決定的で、引き直しで検査を回避できない。
4. **提案者と実行者を分けない。** 計画を書いた文脈が実行を生き、自分の見積りの甘さを同じ文脈で食らう。
   批判・レビュー用のサブエージェントを自発的に増やさない — 検証は宣言の反証手続き（機械・現実）に
   任せ、llm_judgeはOSが監査すると決めたときだけ起こす。

## 儀式はタスク規模に合わせる

台帳登録（手順1）と宣言・納品（手順5-6）は制度の核であり、規模によらず外せない。
それ以外はスケールさせる。迷ったら大タスク側に倒す:

- **小タスク**（変更1〜2ファイル・調査不要・可逆）: Queryは手順2①と②の制約系1本まで
  （①は省略不可 — 規約違反は変更の大きさに比例しない）。noteは実装完了時の1回。
  完了報告は5行以内。宣言は執行可能な反証1本で足りることが多い
- **大タスク**（調査を含む・複数ファイル・不可逆・不慣れな領域）: 手順どおり全て行う

**記録は1タスクにつき2つまで（事前固定PLAN 25行・完了報告50行）。同じ話を3か所に書かない。**

## 手順

0. 新しいセッションの最初の仕事なら、文脈の開始を宣言する:

       node cli/index.js session begin --note "<何のセッションか>"

1. タスクを登録する。**ユーザー依頼はその原文を焼き込む** — objectiveはあなたの言い換えであり、
   意図の曲解は言い換えの瞬間に起きる。原文が無いと、目的適合の判定はあなたの言い換えを
   あなたの成果物と照合するだけの自己参照になる:

       node cli/index.js task new "<objective>" --verbatim "<ユーザー依頼の原文そのまま>" \
         --class "<何をするタスクか（1行の抽象）>" \
         --origin <agenda:項目 | failure:F00x | lesson:S00xx | user> \
         --evaluators <e1>,<e2> --repos <scope>[=<dir>],... --refs <issue-url>

   出力に届くものを読んでから作業に入る:
   - **同種タスクの教訓と実績**（--classが鍵。外れた実績のある教訓に逆らうなら理由を成果物に書く）
   - **較正実績**（この類型の宣言が過去どれだけ実行を生き延びたか、現在の監査率）
   - **評価器の弱体化警告**（同じ類型の過去タスクが判定させていた評価器が落ちていれば警告される。
     意図して外すなら理由を task note に残す。開示のない弱体化だけが禁止される）

   evaluatorの実行先が決まらない登録は失敗する。--repos に対象を足して解決すること。

2. **文脈はQuery経由でのみ取得する**。World Model・events.jsonlの生読みは禁止。
   まず実在するQueryを列挙する（`node cli/index.js query`）:

   | # | 何を | いつ |
   |---|---|---|
   | ① 作法 | 対象リポジトリの禁止事項・検証手段 | **触るリポジトリごとに必ず**（`scope`で引く。省略不可） |
   | ② ドメイン | 仕様・制約・既知の失敗パターン | 話題に応じて（`tag`で引く） |
   | ③ 横断契約 | リポジトリ間の契約・二重実装 | 2つ以上触るなら組み合わせごとに |

   判断の場に立ったら、決める前に引く（LLM推論ゼロの最安経路）:

       node cli/index.js decision recall "<何を選ぶ場面か>"

   ①が `truncated: true` なら `next_offset` で続きを取る。③が0件なのは「まだ記録されていない」
   の意味。実装中に契約を見つけたら手順4で還流する。

3. 計画・実行。**この文脈が計画から納品まで通しで生きる。** 手続きの分業（判定・監査）以外で
   サブエージェントを起こすなら、会話の切り貼りではなくOSに文脈を選抜させる:

       node cli/index.js context --task <id> --purpose "<委ねる仕事>"

   手順を事前に固定したら登録する（変更の禁止ではなく、前後関係の判定可能化）:

       node cli/index.js task plan <id> --file <PLANのパス>

   `task plan` は計画の目的適合briefingを出す。**原文（verbatim）に対する適合**を、
   まだ何も作っていないこの時点でT1サブエージェントに判定させる — 完成後の不適合は
   費やしたものを取り戻さない。人間に上げるのは、本人にしか決められない選好・
   目的の解釈・要求の範囲を変える判断に限る。

   フェーズ境界と重大な発見のたびにチェックポイント:

       node cli/index.js task note <id> "<検証済みの事実・現在のステップ・次アクション>"

   調査・測定を含むタスクでは、成果物に**前提の棚卸し**（出所: ユーザー指定/過去のAI/測定/自分で決めた、
   と各前提への対処）を含める。最も見落とすのは「自分で決めた」前提である。

4. 学習をその場で還流する（タスク終了を待たない）。裏取りした事実・仕様と実装の矛盾・
   運用ルールは発見した時点で書き戻す:

       node cli/index.js statement add "<事実>" --type constraint --tags <t> --scope <repo> --source <裏取り元> --task <id>
       node cli/index.js decision new "<何を決めたか>" --situation "<何を選ぶ場面か>" \
         --options <a,b> --chosen <a> --criteria "<基準>" --expected "<期待>" --task <id>

5. **宣言を登録する。** 成果物が主張していることを1件ずつ、それを剥がす手続きと共に出す。
   これが納品物の正体である — 報告の散文は判定材料にならない:

       # 執行可能な反証（最優先。現実が今すぐ採点でき、トークンを消費しない）
       node cli/index.js claim new <id> "テストが全件通る" --argv '["node","--test"]' --scope <repo>
       node cli/index.js claim new <id> "debugログを残していない" --file-not-matches src/x.js --pattern "console\\.log"
       # 現実・時間が採点する宣言（期限を付けると、期限後にagendaが検収を催促する）
       node cli/index.js claim new <id> "この修正はタイムアウト設定を壊さない" \
         --deferred "運用でタイムアウト起因の障害が出たら剥がれる" --due 2026-09-08
       # ユーザーの検収だけが採点できる宣言
       node cli/index.js claim new <id> "報告は依頼の意図に答えている" --user-settles "ユーザーの検収"
       # どうしても反証手続きが書けない主張は、開示してから納品する
       node cli/index.js claim new <id> "<主張>" --unfalsifiable "<なぜ手続き化できないか>"

   宣言の作法:
   - **成果物が事実上主張していることを宣言から漏らさない。** 検証可能なのに宣言に無い主張は
     検収を逃れる経路であり、判定者はそれを照合する
   - 反証手続きは宣言の内容に届くものにする。常にheldになる手続きは手続きの体裁をした無検査で、
     これも判定者の照合対象である
   - 執行不能な壮大な主張より、**小さくて剥がれうる宣言**が良い納品である。答えられないことを
     答えた体にせず、検証可能な形へ主張を縮める（仕事のスコープは縮めない）

6. 評価と納品:

       node cli/index.js evaluate --task <id>     # deterministic/commandは即時記録
       # llm_judgeのbriefingが出たら、新規サブエージェント（この会話の履歴を持たない）に
       # briefingだけを渡し、指定されたtierのモデルで判定・記録させる
       # 「監査免除」が出たら判定は行われない — 免除の事実とp・根拠を報告に転記する
       node cli/index.js next-action <id>          # FIX等が出たら全部直してから1回で再評価
       node cli/index.js task deliver <id>         # 納品。即時反証を執行し、brokeがあれば失敗する

   deliverの出力に必ず従う:
   - **caveats**は完了報告にそのまま転記する（「全PASSだがこの目的は測れていない」の宣言）
   - **検収待ちの宣言**（deferred/user）と**反証不能の宣言**も完了報告に転記する。
     タスクは delivered であって settled ではない — 現実が採点するまで完了ではない

7. **蒸留してから完了報告する:**

       node cli/index.js statement add "<教訓の1行>" --type lesson --when "<いつ効くか>" \
         --task-class <class_fp> --source <裏取り元> --task <id>
       node cli/index.js task consolidate <id> --lessons <S00x> --helped <S00a> --misled <S00b> \
         [--unapplied <S00c> --unapplied-reason "<理由>"] [--none-learned "<理由>"]
       node cli/index.js decision outcome <S00xx> --result met|unmet --note "<何が起きたか>"
       node cli/index.js experience audit <id>     # 申告の独立監査（T1で起こす）
       node cli/index.js ledger add --purpose run-task --tier T2 --task <id>

   トークン数は実測値だけ入れる（`--tokens-in <n> --tokens-out <n> --measured`）。見積りは入れない。

8. 検収は現実が行い、agendaが催促する。deferredの宣言の結果が分かったら:

       node cli/index.js claim settle <C000x> --result held|broke --evidence "<現実の観測>"

   brokeが出たら較正に恒久記録され、タスクはopenへ戻る。症状をFailureとして起票すること
   （出力が案内する）。**これは罰ではなく価格である** — この類型の監査率が上がり、
   実績を積み直せばまた下がる。

## 運用ヒントの中継

CLI出力の「ヒント:」「警告:」「監査免除:」「開示:」で始まる行は、省略せずユーザーに伝える。
特に「評価が未実行」警告が出ている状態で完了報告を書いてはならない。

## 禁止事項

- 自分の判断でタスクを完了扱いにすること（deliverが通り、検収が閉じるまで完了ではない）
- 宣言なしの納品・報告の散文だけを成果物として登録すること（判定者は散文を証拠として扱わない）
- 剥がれた宣言（broke）を、Failureに起票せず握りつぶすこと
- 監査免除された判定を自分で実行して「PASSだった」と報告に書くこと（免除は免除として書く）
- 批判・レビュー用サブエージェントの自発的な追加（検証は反証手続きと監査抽選の仕事である）
- Queryを経由しない文脈収集（.os/world_model/ の直接読み込み）・events.jsonlの直接編集
- 評価Evaluatorの選定を評価の直前に緩めること・蒸留を飛ばした完了報告
