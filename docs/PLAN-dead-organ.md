# 使われていない器官を名指しする（F011の予防資産）

承認済み提案 `.os/proposals/F011-dead-organ-audit.md` の適用。

## 何を防ぐか

F011 の `why_undetected` は、「器官が正しく動くか」（単体テスト・golden task）と
「成果物が要件を満たすか」（evaluator）の2層はあるのに、**「器官が実際に使われたか」を
見る層が無い**というものだった。decision/policy の単体テストは全件PASSで、テストの中では
閉ループが成立していた。実運用の記録（`policy.active=0` / `hits=0` / outcome 0件）は
`metrics` に出ていたが、ゼロを問題として名指しする経路が無く、3文脈・15タスクのあいだ
誰も読まなかった。

## 何を作るか

`agenda` に材料を1種類足す（`kind: dead_organ`）。判定はすべて既存台帳の算術で、LLMを呼ばない。

- 器官の表（器官名・記録の在り処・0件が意味すること・次の一手）をコアに持つ。
  載せるのは**設計上、通常運用で必ず記録が生じるはずの器官だけ**（正当に0件でありうる
  `research` 等は載せない）
- 記録が0件の器官を項目として出す。**強制はしない** — 出すのは事実だけで、
  「使え」とも「消せ」とも言わない（負債の返し方は使うと捨てるの両方がある。S0018）
- 抽出が壊れたら沈黙せずNGにする（F008: 抽出不能を「違反ゼロ」と報告しない）

## 提案からの逸脱（先に書く）

提案の受け入れ条件は「器官の記録を消したfixtureで項目が出ること、記録があるfixtureでは
出ないこと」をgolden taskで検査せよと書いている。**この形は採らない。**
それは*コードの性質*（材料が実装されているか）であって*データの性質*ではなく、
fixtureで両方向を作ろうとすると判定ロジックの複製をfixtureに置くことになる
（F008の再現。T014でも同じ理由で同型のgoldenを取り下げた）。

代わりに:
- 「0件なら出る / 記録があれば出ない」は**単体テストで両方向**を固定する
- golden task は**データ側の性質**を検査する: 器官の記録に壊れた行があるfixtureはFAIL、
  すべて読めるfixtureはPASS。読み飛ばして0件と数える実装に戻すと赤くなる

## 受け入れ条件

**この文書は実装の後に書いた。事前固定ではない。**
F011は承認済み提案（受け入れ条件を含む）が先にあり、実装はそれを追ったが、
この計画書自体は実装後の記述であり、下の条件は結果を見た後に書かれている。
台帳の登録時刻（`task plan` の ts と `task artifact` の ts）から誰でも確認できるため、
ここで先に開示しておく。事前固定の効き目を主張できるのは提案側の受け入れ条件だけである。

1. 記録が0件の器官が `agenda` に `dead_organ` として出る。記録が1件でもあれば消える（単体テスト）
2. 仕事を1周していないOSでは1件も出ない（初日のOSに負債を並べない）
3. 記録が読めないとき、0件と数えず警告として出る（単体テスト）
4. golden task: 壊れた行のあるfixtureでFAIL、読めるfixtureでPASS
5. `node --test` 全件・`regression` 全件（golden 14件）・docs-drift・skill-commands が通る
6. 実測: 本体に対して実行し、実在の「動いていない器官」が名指しされること
   （0件しか出ないなら、この層は何も見ていない）

## 前提の棚卸し

| 前提 | 出所 | 対処 |
|---|---|---|
| 残タスク（F011適用を含む）を進める | ユーザー指定 | 固定制約 |
| 名指しはするが強制はしない | 提案 | 固定制約。scoreは提案と同じ最下層に置く |
| 表に載せる器官の選定 | 自分で決めた | 6件（policy / policy_hit / decision_outcome / measured_tokens / delivered_context / claim_audit）。いずれも run-task を1周すれば記録が生じる |
| 「1周した後も0件」を条件にする門 | 自分で決めた | 受け入れ条件2で固定。門が無いと新規OSが常に6件の負債を出す |
