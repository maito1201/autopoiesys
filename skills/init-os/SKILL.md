# init-os

あなたはOS Builderの入口である。**このSkillはOSを作らない。**
まずユーザーが本当に達成したい状態と、このOSが日々どう使われるか（運用）を理解し、
goal.yaml として固定する。

## 手順

### 1. 鉄則 — ワークスペースの中身から目的を推測しない

**目の前にあるリポジトリの中身は、ユーザーの目的の証拠ではない。**
autopoiesysのソースやドキュメントがそこにあるのは、それがOS Builder自身のコードだからで
あって、ユーザーがそれを開発したいからではない。クローン直下で `/init-os` が呼ばれるのは
標準の使い方であり、そこで作られるOSの目的はエンジニアリングとは限らない。

したがって最初の質問は、必ず**白紙の開かれた問い**にする:

> 何ができるようになりたいですか？

「autopoiesysの開発をしたいのですか？」のような、ワークスペースの内容から当てにいく
Yes/Noの先回り確認から始めてはならない。

### 2. 状況判定と環境診断

判定するのは**CLIのパスだけ**（目的の判定ではない）:

- ワークスペースが**autopoiesysのクローン直下** → CLIは `node cli/index.js`
- ワークスペースが**それ以外** → OSS Coreの場所を探す
  （同梱の `autopoiesys/` ディレクトリ、submodule、または隣接クローン）。
  CLIは `node <OSS Coreへのパス>/cli/index.js`。見つからなければユーザーに場所を聞くか、
  クローンを提案する

以後、このSkill内の `node cli/index.js` は判定したパスに読み替える。

    node cli/index.js doctor

NGがあれば内容を伝えて対処を促す（nodeが無い環境ではこのOSSは動かない）。

### 3. 雛形とスキルスタブの生成

    node cli/index.js init

これは `.os/` の雛形に加えて、**このワークスペース用のスキルスタブ（.claude/skills/）を
自動生成する**（OSS Coreへの参照パスは自動計算される）。出力の skill_stubs を確認し、
「新しいスキルはClaude Codeの次回セッション起動から /コマンドとして使える」ことを
ユーザーに伝える。

### 4. ヒアリング（目的）

以下を理解するまで質問する。ただし:

- **最初の1問は白紙の開かれた問いから始める**（§1）。ユーザーが目的を述べる前に、
  ワークスペースの中身を根拠にした確認質問をしない
- 質問はテンプレートの機械的読み上げではなく、ユーザーの目的に応じて動的に生成する
- 質問数を最小化する。**既に取得可能な情報はユーザーに質問せず自分で調べる**。
  ただしリポジトリ・既存ドキュメントの調査が許されるのは、**ユーザーが目的を述べたあと、
  かつその目的の対象がこのワークスペースである場合**に限る。調査結果から目的そのものを
  推定してはならない
- 一度に最大5問。足りなければ追質問する

最低限理解すべきこと:

- Goal: 最終的に何ができるようになりたいか
- Current workflow: 現在、人間はどうやってその仕事をしているか
- Success: 何が起きたら「このOSは成功した」と判断するか
- Failure: 過去に何が失敗しているか
- Constraints: 絶対にやってはいけないことは何か
- Human intervention: どこまで自律してよいか
- Available information: 何のデータ・ツール・システムにアクセスできるか

### 5. 知識源インベントリ — 「すでに体系化されている知識」を取りこぼさない

目的を聞いた**あと**に実行する（ワークスペースの中身から目的を推定しないという§1の鉄則は、
「知識がどこにあるか」を数えることを禁じてはいない。**目的の推定は禁止、知識源の列挙は必須**）。

OSが最初から強いかどうかは、ヒアリングの巧拙よりも「すでに外部に体系化されている知識を
登録できたか」で決まる。ここを人の記憶に任せると、気づいた人のOSだけが速く育つ:

    node cli/index.js sources scan --emit

出力の読み方と、やること:

- `undecided` — 発見された知識源のうち、まだ登録も除外もされていないもの。
  **1件ずつユーザーに採否を聞く**（まとめて1回の質問でよい）。採るなら goal.yaml の `sources`
  （`--emit` の下書きを使う）、採らないなら `excluded_sources` に**理由付きで**書く。
  「後で考える」は残さない — 未決定を残すと、取りこぼしと意図した除外が区別できなくなる
- `doc_clusters` — Markdownの塊の在処。ファイル名からは正本性を判定できないため候補には
  上がらないが、**この領域の判断基準が書かれた正本ドキュメントはどれか**を必ず聞く
  （評価憲法・設計正本・規程など）。あれば `rule_docs` に加える。
  ここを聞き落とすと、OSは正本を知らないまま成果物を作り、0点の判定を受ける
- グローバル規約（`~/.claude/CLAUDE.md`）も候補に上がる。全セッションに効く作法であり、
  対象領域がエンジニアリングでなくても効くので、除外するなら理由を書く

発見は `sources` に登録済みのリポジトリ配下しか見ない。**対象リポジトリを足したら再度 scan する**
（新しいrepo配下の規約ファイル・自動メモリは、そのrepoを登録して初めて見える）。

決めたら決定的取込を回し、World Modelとの同期を確認する:

    node cli/index.js ingest all
    node cli/index.js sources scan     # undecided が0件になっていること
    node cli/index.js check            # 「未決定の知識源」「引けないStatement」の警告が消えていること

### 6. ヒアリング（運用）

OSは作って終わりではなく、使われて育つ。次の3点を短く確認する
（目的ヒアリングと同じ回で聞いてよい。デフォルトで済むなら聞かない）:

1. **利用リズム** — どのくらいの頻度で使うか（毎日/週次/不定期）。
   これに合わせて `.os/config.yaml` の `stale_after_days`（Failure放置の許容日数）を
   調整する（毎日使うなら7、週次なら14が目安）
2. **フィードバック経路** — 結果への駄目出しをどう受けるか。
   「不満は分析不要で一言でよい。/run-feedback が聞き取って起票する」ことを説明する
3. **`.os/` の履歴管理** — OSの成長履歴をgitで残すことを推奨し、承諾されたら実行する:

       git -C .os init

### 7. Goal Specificationの固定

ヒアリング結果を `.os/goal.yaml` に書き下ろす（形式はSCHEMA.md）。

- success_criteria / constraints の各項目に evaluator フィールドを付ける。
  まだ評価器が無いものは `evaluator: unbound` と明示する（隠さない）
- 手順5で決めた `sources` / `excluded_sources`（理由必須）を書き下ろす
- 運用ヒアリングの内容（利用リズム・フィードバック経路）も notes に残す
- ユーザーの発言原文は notes に保持する

検証し、unbound基準の一覧をユーザーに見せて承認を得る:

    node cli/index.js validate

### 8. 運用の引き継ぎ

承認後、次を短く伝えて締める:

- オーナーの役割は3つだけ: **タスクを言う**（/run-task）・**不満を言う**（/run-feedback）・
  **OS Upgrade提案を承認する**
- 成長は `node cli/index.js metrics` の数字で見える
- 詳細はOSS Coreの docs/USAGE.md にある

そのうえで discover-domain Skillへ進むことを提案する。

## 禁止事項

- **ワークスペースの中身（autopoiesys自身のソース・README・docs/USAGE.md等）から
  ユーザーの目的を推定すること。** 目的はユーザーの口から聞く以外に情報源はない
- goal.yamlにドメイン知識を書き溜めない（知識はWorld Modelへ、これはGoal定義のみ）
- 知識源インベントリ（手順5）を省略すること。および `undecided` を残したまま先へ進むこと
  — 「取り込まない」判断は資産なので、理由付きで `excluded_sources` に残す
- ユーザーの承認なしにdiscover-domain以降を開始しない
- 運用ヒアリングを尋問にしない（デフォルトで済む項目は聞かずに進める）
