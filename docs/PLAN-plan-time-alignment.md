# 計画の目的適合を、作り始める前に判定させる

## 受け入れ条件（実装の結果を見る前に固定する）

1. `task plan` が計画レビューのbriefing（`.os/briefings/plan-<task>.md`）を自動生成する。
   渡す材料は goal.yaml（目的・成功基準・制約）・確立済みの方針・計画本文だけで、
   実行者の説明・完了報告・会話履歴は含まない
2. briefingのrubricが、目的からの導出・領域の差し替え可能性・既存の道具との重複・
   診断と解法の順序・目的の縮小を問う
3. 判定は独立サブエージェント（T1）が行い、`plan_alignment` として記録される。
   **人間に確認を上げる経路は作らない**
4. 確立済みの方針が0件のときは「無い」と明示する（無いことを隠さない）
5. `node --test` 全件・`regression` 全件・docs-drift・skill-commands が通る
6. 自己適用: この計画自身をこの装置で判定させ、verdictを記録する

## 前提の棚卸し

| 前提 | 出所 | 対処 |
|---|---|---|
| 計画登録の時点で目的適合を判定させる | ユーザー指定（「これは正しいので進めよう」） | 固定制約 |
| 装置は判断材料を供給する。確認・強制・監視はさせない | ユーザー指定 | 固定制約。判定者はサブエージェントに限る |
| 受け入れ条件が設計判断の符号化地点である | 自分で決めた | load-bearing。外れていれば、この装置は短絡を捕まえられない |
| 完成物への判定より安い | 測定（完成物の判定は95k〜122k、計画は25行） | 実測を報告に載せる |
