# 実運用エビデンス — 独立評価が何を検出したか

autopoiesys で生成した株式トレード研究OS（以下「研究OS」）を2日間実運用した記録。
「素のLLMに指示するより良い仕事をする」という主張の根拠を、第三者が検証できる形で残す。

一次資料は研究OS側の `.os/`（独立したgitリポジトリ。タグ `os-v1-before-F002-upgrade`、
`os-v2`、`os-v3`）と `research/`・`report/` 配下のファイルである。

## 何を測ったか

研究OSは5分足の株価パネル（333銘柄 × 66営業日 × 142万本）を対象に、
デイトレードの取引ルールを探す研究を2タスク（T001・T002）実行した。
評価は毎回、**生成側の会話履歴を持たない独立サブエージェント**が
briefingだけを読んで PASS / FAIL / UNCERTAIN を記録した。

## 事例1: 生成側が5回気づけなかった測定装置の欠陥を、独立評価が検出した

### 何が起きたか

立会時間の分を「取引経過分」に直す写像が `m < 690` で分岐しており、
**前場引けの11:30バー（銘柄日の99.0%・21,714件に存在）が10:30と同じ値に落ちていた**。

影響は2つ。

1. 10:30の断面に1時間先のデータが混入し、同時刻の全銘柄平均・セクターピア・
   断面順位がすべて汚染された
2. 銘柄日の中で時刻が 145 → 90 → 150 と逆行し、前方参照に使っていた二分探索
   （昇順が前提）が壊れ、「30分保有」の一部が実際には35〜85分保有になっていた

この欠陥の上で「相対方向は標本外で予測可能（断面IC +0.0263, t=4.24）」という
結論が出ていた。修正後は **+0.0105（t=1.44、上位3日除去で+0.0028）** で、有意でない。

### 誰が検出したか

- **評価器8本のうち7本はPASSを出した。** 7本はいずれも生成側が書いた報告を読み、
  その内部整合（先読みの記述・ベースラインの併記・検出下限の記載）を検査するものだった
- **検出したのは1本だけ**で、それは報告ではなく**実装コードを読んだ**評価器だった。
  この評価器はパネルを自分で開き、銘柄日内の時刻非増加が21,714件あることを確認した
- 生成側の自己点検も効かなかった。生成側は同じ研究の中で、より極端な欠陥
  （断面IC 0.298、t=74.6）は「良すぎる数字」として自力で検出している。
  **もっともらしい範囲（t=4.24）に収まる欠陥は通した**

### 何が残ったか

検出器 `measurement_device_invariants`（T0・command）。時間軸の写像について
厳密増加・値の衝突なし・昼休みが詰まっていること・実データでも同様、を検査する。
Golden Task `gt-002` に組み、欠陥を再導入した fixture で実際にFAILを出せることを確認済み
（違反3件を検出）。正しい写像の fixture ではPASS。

## 事例2: 報告の追随漏れを、独立評価が4回連続で検出した

装置の欠陥を直して全21測定を再実行したあと、報告の一部だけを直して他を直し忘れる、
という抜けが4回続いた。**4回とも独立評価が見つけ、生成側は一度も自分で見つけていない。**

| 回 | 見逃していた箇所 | 実際の値との差 |
|---|---|---|
| 1 | 完了報告だけが再測定前の数値を保持 | 標本外IC +0.0263(t=4.24) ↔ 実出力 +0.0105(t=1.44) |
| 2 | 運用形の表と「次に測るなら」節 | 日次 -0.1196% ↔ -0.1165%、スプレッド +0.148% ↔ +0.113% |
| 3 | 反証節のz値の範囲 | 「z=+3.5〜+5.2」↔ 実測 -1.94〜+4.60（12値中8値が+3.5未満） |
| 4 | プラセボ平均の範囲・バリア幾何の列範囲 | 片方の事象・別の列の値を範囲の端に使用 |

**3件は主張に有利な向きに外れていた**（分離を強く見せる・広がりを小さく見せる）。
意図的ではないが、結果として都合の良い方向へ偏っていた。これが
「Agent自身の完了宣言を信用しない」という設計判断の実測的な裏づけである。

### 何が残ったか

検出器 `report_matches_measurements`（T0）。報告に書かれた数値が測定JSONの実出力に
実在するかを照合する。許容誤差は書かれた桁数の半分から決める（固定の絶対値にすると
bp表記と%表記で意味が変わり誤検出する）。Golden Task `gt-004`。

## 事例3: 前提の無検証な継承と、その予防を誤った話

### 何が起きたか

研究が行き詰まったとき「過去の履歴で前提に置いてる考え方から疑って」という指摘を受けた。
生成側の対応は、**古い前提を捨てて別のセッションのAIが作った規則に乗り換えること**だった。
乗り換え先がなぜ存在し誰の決定なのかを確認せず、存在しない違反（封印期間の汚染）を
「不可逆の損害」として報告した。実際には、その封印期間は機械学習プログラム用に
定められたもので、当該研究はルールベースだったため適用されなかった。

### 予防資産を最初は誤って設計した

第1版の予防策は「前のAIが作った規則に従うことを強制する検出器」だった。
**これは前提を機械に焼き付ける行為で、同じ失敗の再現である。**
第2版では設計を反転させ、`premise_disclosure`（T0）は
**どの前提が正しいかを一切決めず**、採用した前提が出所つき
（ユーザー指定 / 過去のAI / 測定 / 自分で決めた）で開示されているかだけを検査する。

この経緯自体が、CONCEPT §26⑦「OS Upgradeを局所修正にしない」の実例になっている。

## 事例4: 破棄した検出器2本（正直な記録）

検出器を作れば必ず良くなるわけではない。**誤検出する検出器は無視されるだけで、
検出力より先に「正しい状態で鳴らないこと」を確かめる必要がある。**

| 検出器 | 何を狙ったか | なぜ破棄したか |
|---|---|---|
| 先読みの静的パターン照合 | `op[ex[ok]] / op[ok]` という式を違反として検出 | **正しいコード11箇所を誤検出**。同じ式が正しい形（各行を建値とする配列を作り下流で建玉行を選ぶ）でも出るため、式だけでは正誤を区別できない |
| 範囲表現の照合 | 報告の「A〜B」が実出力の集合の端と一致するか検査 | **15件中ほとんどが誤検出**。範囲は分析者が選んだ部分集合に対するもので、正当な部分集合を機械で列挙するのは原理的に不可能 |

どちらも、**設計を変えることで目的を達成した**。

- 先読み → 前方リターンの計算を `common.py` の3関数に集約し、
  「集約が破られていないか」だけを検査する形にした
  （分足の読み込みを共通モジュールに集約する既存の慣行と同じ形）。
  21本を付け替えたうえで全21ファイルの出力が数値まで一致することを確認した
- 範囲 → 測定スクリプト側が範囲を計算してJSONに出力する形にした。
  これで報告の両端はJSONの実在値になり、既存の数値照合がそのまま効く

## 事例5: Failure が検出器と回帰テストに変換された

ユーザーの不満（「なんで勝てなかったか考えて」の一言）から始まり、
3件のFailureが `reported → investigated → classified → upgrade_proposed → implemented`
の状態機械を通り、以下の資産に変換された。

| Failure | 分類 | 生まれた資産 |
|---|---|---|
| F001 前提の無検証な継承 | missing_evaluator | `premise_disclosure` + `gt-001` |
| F002 指摘への対応が同じ失敗の再現だった | missing_evaluator | 上記の設計反転 + Query に provenance を追加 |
| F003 測定装置の時間軸の欠陥 | missing_evaluator | `measurement_device_invariants` + `forward_return_aggregation` + `report_matches_measurements` + `gt-002/003/004` |

**すべてのgolden taskが検出力テストを含む**（欠陥を再導入した fixture で実際にFAILを出せること、
かつ正常な fixture でPASSすること）。`node cli/index.js regression` は 4/4 で通る。

### 副次的に見つかったコア側の穴

実運用の中で、OSSコア自身の欠陥が3件見つかった。いずれも提案として起票済み。

- llm_judge に文書だけを渡している状態をコアが検出しなかった
  （→ briefingに実装の有無を明記し、運用ヒントで警告するよう修正済み）
- 誤ったOS Upgrade提案を差し替える状態遷移が存在しない
- 検出力不足で目的が原理的に達成不能な状態を、コアが FIX としか表現できない

## 事例6: 評価が全通過した成果物が、目的を取り違えていた（この仕組みの限界）

autopoiesys本体の改善タスクで Decision Model を実装した。決定を選択肢・基準・期待結果・
**レビュー期限**を持つ構造として記録し、期限切れをCLI出力で催促する設計だった。

- 決定的評価3本すべてPASS
- 独立サブエージェント（生成側の履歴を持たない）による llm_judge も **PASS**。
  判定者は報告を信じず実物のコード行を読み、テストを自分で実行して確認していた
- `next-action` は DONE を返した

**それでも成果物は誤っていた。** ユーザーの指摘は「期限とか催促とか意味わからん」。
autopoiesysで「意思決定支援」と言うときの支援対象は**AI自身**であって人間ではない。
作られたのは人間向けの帳簿で、AIが決める瞬間に効く経路はどこにも無かった。

### なぜどの検出器も気づかなかったか

evaluatorはすべて「実装がobjectiveどおりに存在するか」を検査していた。
**objective自体が誤った対象を指していた場合、この構造は原理的に検出できない。**
独立評価も同じ穴に落ちる — 判定者はbriefingに書かれた目的を所与として読むからである。

これは「独立評価が生成側の見落としを検出する」（事例1・2）の裏面であり、
**この仕組みが何を検出できないかの実例**である。目的の妥当性は、
現時点では人間の指摘でしか入ってこない。

### 何が残ったか

検出器 `policy_falsifiable`（T0・command）と Golden Task `gt-003`。
ただしこれが検査するのは目的の妥当性ではなく、作り直した方針層の**状態の不変条件**
（反証された方針が発火し続けていないこと）だけである。
**目的の取り違えそのものを検出する資産は作れていない。**

## 事例7: 実装されていたのに一度も動作しなかった器官を、台帳の記録が名指しした

### 何が起きたか

意思決定の層（決定を記録し、結果を照合し、反復した判断を「方針」へ畳み込んでLLM推論なしに
発火させる仕組み）は実装され、単体テストは全件PASSしていた。しかし3つの文脈（セッション）・
15タスクの実運用を経た時点で、機械記録は次のとおりだった。

- 記録された決定: 6件
- 結果（met/unmet/unclear）が記録された決定: **0件**
- 確立された方針: **0件**、方針の発火: **0回**

つまり「決めた通りになったかを照合するループ」は、存在はしていたが一度も閉じていなかった。

### 誰が検出したか

人間の指摘ではなく、`metrics` と `decision list --unreviewed` の出力である。
ただし**その数字は3文脈のあいだずっと出力されていた**（誰も読まなかった）。
「ゼロであること」を問題として名指しする経路がOSに無かったことが、この事例の核心である。
単体テストは全件通っていた — テストの中では閉ループが成立していたためで、
**装置の存在と装置の作動を取り違えていた**（F008「検証装置が検証対象の複製を検証していた」と同族）。

### 原因（コードで確認したもの。推測ではない）

1. 判断の場の同定に選択肢の文字列を含めていたため、同一の場でも選択肢の書き方が違えば
   別の場として記録された。台帳の決定は全件が別の場になっており、再来が一度も起きていなかった
2. 過去の決定を実行者に届ける経路が pull（自分で `decision recall` を呼ぶ）しか無かった。
   教訓の層は task 登録時に黙って押しつける経路（push）を持ち、配信56件の機械記録がある。
   **押しつける層は動き、引きに来させる層は死んだ**

### 何が残ったか

- 場の同定から選択肢を外し、過去の記録は読み出し時に統合する（台帳は追記専用のまま）
- 過去の決定をタスク開始時の想起に混ぜて配る。配信したIDは `context_log.jsonl` に残るので、
  「届いたのに結果が記録されなかった決定」を自己申告に依存せず数えられる
- 完了したタスクで下した決定に結果が無ければ、運用ヒントと `agenda` が出し続ける
- Failure F011（severity high）として台帳化。予防資産（使われていない器官を名指しする仕組み）は
  提案として `.os/proposals/F011-dead-organ-audit.md` に置き、**未適用**のまま承認待ちにしてある

修正の直後、同じ判断の場（「自己検証の判定基準をいつ固定するか」）が別の文脈で再来し、
前回の選択と結果が返り、**この台帳で初めて方針が1件コンパイルされた**
（`policy.active: 1 / hits: 1`）。これは主張ではなく `.os/rules/policy-e6d61b1e.yaml` と
`observations/context_log.jsonl` から再構成できる機械記録である。

## 事例8: 判定コストの支配項は「1本の大きさ」ではなく「本数」だった

同じ類型（コアの器官を実装し独立評価で完了認定する）のタスクで、判定側の消費を
機械記録から比べた。数値は `observations/context_log.jsonl` とサブエージェントの実測である。

| タスク | briefing合計 | 本数 | 判定サブエージェント |
|---|---|---|---|
| T016（旧） | 85,873 | 20 | 6本・5ラウンド・561k |
| T017 | 1,975 | 1 | 1本・122k（＋監査82k） |
| T019 | 2,029 | 1 | 1本・115k（＋監査107k） |
| T020 | 1,962 | 1 | 1本・95k（＋監査101k） |

削減前の想定は「briefingが大きいから削る」だったが、実測すると briefing 1本は 3.7k で、
その66%（3,951トークン）は evaluate のたびに全履歴が積み上がる「検証実績」節だった。
**当初狙った Artifact の畳み込みは166トークンしか効いていない。**

効いたのは3つ: ①検証実績とArtifactを項目ごとの最新1件＋推移1行へ畳む
②指摘をまとめて直してから1回だけ再評価する（1指摘ごとに回すと判定1本が指摘の数だけ走る）
③同一状態の再判定を機械的に止める（`skipped: unchanged`）。
**支配項は本数で、20本→1本が最大の寄与である。**

削らなかったもの: 判定者の探索範囲。自分で確かめることが独立評価の値打ちであり、
そこを削ると安くなった代わりに検出力が落ちる。実際、削減後の判定でも
実行者の虚偽申告1件と根拠のない主張1件が捕まっている。

## 事例9: 判定器を1つ落としたことが、5タスクのあいだ誰にも見えなかった

実行者はタスク登録時に評価器の集合を自由に選ぶ。T017の登録で、前タスクの `--evaluators` を
引き写した結果、`objective_alignment`（「objectiveがgoalに仕えているか」を見る唯一の層。
F005/F004由来）が宣言から落ちた。意図した除外ですらない。以後 T018〜T021 の5タスクが
その状態で完了認定を通った。

**量的な監視では原理的に見えなかった。** 評価器の件数は 9→7→8→9→9 と推移しており、
落ちた3件は新設した検出器の増設に隠れていた。`objective_alignment` は goal.yaml の
success_criteria に束縛されていないため unbound監査・gap分析・caveats にも現れず、
`dead_organ` 検出は「一度も記録が無い器官」を見るので、
**使われていたのに使われなくなった器官**は対象外だった。

その状態で作られた成果物（判定コスト削減のためのリポジトリ専用の目次生成器）は、
ドメイン固有で既存ツールと重複する短絡だったが、**宣言された受け入れ条件への適合としては
完全だった**: 独立判定2回ともPASS（evidence 14件・12件）、golden 14/14、検出器全件 exit 0。
短絡を指摘したのは人間である。

是正後、`objective_alignment` をT021に復帰させて実行したところ、**初回で FAIL を返した** —
「実装から目次生成を破棄したのに、台帳のObjectiveは3要素のまま。目的の縮小が記録に
反映されていない」。requirement_satisfied の判定2本（合計20万トークン超）が見つけなかった
欠陥を、T1（安価モデル）の判定1本が捕まえた。

予防は「集合を同じ類型どうしで比べる」ことにした（`check-evaluator-drift.js` / gt-015）。
落とすこと自体は禁止しない — 何を判定させるべきかをコアが決めれば、内容を機械に
焼き付けることになる。禁止するのは**開示のない弱体化**だけである。
検出器は初走行で実在の違反6件（T016〜T021）を捕まえた。

なお T021 は DONE にしていない。破棄した要素をObjectiveから消せば記録は整合するが、
**目的を結果に合わせて縮めるのは最も危険な短絡**であり、その経路はコアに用意していない。

## この文書の限界

- **A/B比較は未実施。** 「素のLLMに同じ仕事をさせた場合」との対照実験は行っていない。
  上の事例が示すのは「独立評価が生成側の見落としを検出した」ことであって、
  「OSなしでは検出できなかった」ことの証明ではない。
  対照実験の手順は `docs/experiments/baseline-comparison.md` にある
- **トークン消費の比較も未実施。** 現時点で briefing は Query 結果の全文を埋め込むため、
  「ナレッジグラフを超えるトークン経済」は主張できる段階にない
- 事例はすべて単一ドメイン（株式トレード研究）・単一の運用者によるもの
