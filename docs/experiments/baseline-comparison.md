# 実験手順: OSあり / OSなし の対照比較

`docs/EVIDENCE.md` に記録した事例は「独立評価が生成側の見落としを検出した」ことを示すが、
「OSなしでは検出できなかった」ことの証明にはなっていない。この手順書はその対照を取る。

**この文書は手順の事前固定である。実行前に読み、実行後に書き換えない。**
変更が必要になったら、変更内容と理由を末尾の変更履歴に追記する。

## 検証する仮説

> 同一の仕事を、素のLLMエージェントに実行させた場合と autopoiesys の生成OS上で
> 実行させた場合を比べると、**最終成果物に残る欠陥の数**が後者で少ない。

反証されるべき対立仮説を先に置く。

- H0-a: 差は無い（OSの儀式はトークンを消費するだけで、欠陥検出に寄与しない）
- H0-b: 差はあるが、それは「独立した第三者に検分させた」ことだけで説明でき、
  World Model・Query・Failure学習は寄与していない

H0-b を切り分けるため、条件は3つ置く（下記）。

## 条件

| 条件 | 内容 |
|---|---|
| **A: 素** | Skillなし・OSなし。タスク文だけを渡して実行させる |
| **B: 検分のみ** | Aと同じ実行のあと、独立サブエージェントに成果物を検分させる（World Model・Query・Failure台帳は与えない） |
| **C: OSあり** | 生成OS上で run-task の手順どおりに実行する（Query経由の文脈取得・独立評価・next-action） |

B と C の差が、**「第三者の検分」を超えた部分**（蓄積された知識・検出器・回帰）の寄与にあたる。

## タスクの選び方（事前固定）

- 実行前にタスクを3件選び、この文書に**タスク文をそのまま書き留めてから**開始する。
  実行後に選び直さない
- 3件は性質を分ける: (1) 実装タスク (2) 調査・測定タスク (3) 既存成果物のレビュー
- **正解が事後に検証可能**であること（テストが書ける・数値が再計算できる、など）。
  「良い設計か」のような検証不能な課題を選ばない
- 各条件・各タスクで3試行。計 3条件 × 3タスク × 3試行 = 27回

## 測定項目

すべて事前に定義し、実行後に追加しない。

| 項目 | 取り方 |
|---|---|
| 残存欠陥数 | 全27成果物を、条件を伏せた状態で同一の検分者が採点する（下記「採点」参照） |
| 検出された欠陥数 | 各条件の過程で検出・修正された欠陥の数 |
| 自己申告のまま通った欠陥 | 「完了」と報告されたが残存欠陥がある回の数 |
| 消費トークン | `observations/context_log.jsonl` と `query_log.jsonl` の実測（条件Cのみ）。A・Bはセッションの実測値 |
| ループ数 | 完了までの evaluate → next-action の往復回数（条件Cのみ） |

**「タスクを完了した数」を成功指標にしない**（CONCEPT §18: 大量の仕事を完了したことを
成功としない）。最重要は残存欠陥数である。

## 採点

- 採点者は**条件を知らされない**（成果物のファイルだけを渡す。ディレクトリ名・
  ログ・タスクIDから条件が推測できないよう、採点前に匿名化する）
- 採点基準は実行前に書き、タスクごとに固定する
  （例: 実装タスクなら「テストが通る」「仕様の各項目を満たす」「既存の振る舞いを壊さない」）
- 欠陥は「客観的に指摘できるもの」に限る。好みの問題は数えない

## 判定

- 主要な比較は **C 対 B**（第三者検分を超えた寄与があるか）
- 副次的に **B 対 A**（第三者検分そのものの寄与）
- 試行が各9回（3タスク×3試行）と少ないので、**t検定のような有意性判定はしない**。
  報告するのは各条件の欠陥数の分布（全値を列挙）と、タスクごとの対応差である
- **検出力が足りないことを先に認める。** 差が出なかった場合に
  「差が無い」とは書かない。「この試行数では検出できない」と検出下限つきで書く

## やってはいけないこと

- 結果を見てからタスクを選び直す・測定項目を足す・採点基準を変える
- 条件Cだけ実行者が丁寧にやる（3条件とも同じ人・同じ日・同じ順序規則で回す）
- 良かった試行だけを報告する（27回すべての結果を列挙する）
- 「OSあり」の成果物にだけ追加の推敲をする
